2. **용량이 병목이었다. yolo26s 로 갈아탈 것 (2026-09-09).**

   ```
              P        R    mAP50   mAP50-95   train/cls  val/cls
   yolo26n  0.8658   0.7946  0.8575   0.6495      2.000    1.873
   yolo26s  0.9065   0.8473  0.9043   0.7288      1.394    1.384
   ```

   전 지표가 낫고 train/val 손실이 **둘 다** 낮다. s 는 34 epoch 에서 n 이
   184 epoch 걸려 도달한 최고값(0.7053)을 넘었고, 60 에서도 여전히 오르는 중이었다.

   운영 가중치와 비교해도 그렇다. **60 epoch 짜리가 이미 앞선다:**

   | 가중치 | imgsz | mAP50-95 | 추론 |
   |---|---|---|---|
   | n ft960 (현재 `best.pt`) | 960 | 0.7239 | 4.58ms |
   | **s probe 60 epoch** | **640** | **0.7311** | **4.47ms** |

   **추론 비용이 같다.** s@640 이 n@960 과 같은 시간에 돈다.

   클래스별로는 희소 클래스가 오른다 — bus +0.045 / scooter +0.018 / truck +0.011,
   대신 person −0.010 / car −0.011 (원래 강했던 것들).

   **s 에서는 해상도를 올릴 이유가 없다. `predict.imgsz` 를 640 으로 되돌릴 것.**

   | imgsz | mAP50-95 | 640 대비 | (참고) n 은 |
   |---|---|---|---|
   | **640** | **0.7311** | — | 0.7050 |
   | 960 | 0.7294 | −0.0018 | 0.7193 (**+0.0143**) |
   | 1280 | 0.6810 | −0.0501 | 0.6959 (−0.009) |

   n 은 960 이 정점이었지만 s 는 640 이 정점이고, 1280 손실도 5배 크다.
   640 을 두 번 재서 소수 4자리까지 같았으니(val 은 증강이 없어 결정적)
   −0.0018 은 잡음이 아니다. 다만 작아서 "960 이 낫다고 할 수 없다"까지만 말할 수 있다.

   **"용량이 늘어 640 에서도 작은 객체를 잡기 때문"은 틀린 설명이었다.** 클래스를
   크기 순으로 놓고 640→960 변화를 보면 정반대다.

   ```
   motorcycle  317  0.6657 -> 0.6634  -0.0022   <- 가장 작은데 평평
   scooter     176  0.5884 -> 0.6033  +0.0150
   bicycle     281  0.6578 -> 0.6362  -0.0216
   person    4,718  0.7895 -> 0.8034  +0.0139
   car       2,207  0.8733 -> 0.8857  +0.0124
   truck       262  0.7296 -> 0.7467  +0.0171
   bus         219  0.8137 -> 0.7668  -0.0470   <- 가장 큰데 폭락
   ```

   960 은 person·car·truck·scooter 를 올리는데 bus·bicycle 이 그만큼 깎아
   총합이 평평해진 것이다. **왜 bus 가 깎이는지는 아직 설명하지 못했다.**
   그 둘은 박스가 219·281개뿐이라 표본도 얇다. 총합 결론(640 을 쓸 것)만 쓸 것.

   VRAM 실측 (8GB 카드, AMP): s@640 은 **batch 16 이 상한**이다.

   ```
   n 640 b40   6.19 GiB    385 ms/step
   s 640 b40  10.93 GiB   6866 ms/step   <- OOM 없이 페이징. 함정 9 그대로
   s 640 b24   6.61 GiB    650 ms/step
   s 640 b16   4.47 GiB    220 ms/step   <- 실제 학습 259초/epoch
   s 960 b8    5.15 GiB    244 ms/step   <- BN 이 불안정해 권하지 않음
   ```

   **프로브를 이어 가지 않고 본 학습을 새로 돌렸다.** seed2 추가·폴더 이동으로 데이터가
   바뀌어 `labeler.py train` 으로 처음부터 시작했다 — `runs/train-3` (yolo26s / 640 /
   batch 20 / patience 120 / close_mosaic 30). 두 번 이어 붙였고(26·72 epoch 에서)
   **202/300 에서 정지 파일로 멈췄다.** best 는 epoch 158 (mAP50-95 0.7390).
   프로브의 resume.pt 는 2026-09-11 정리 때 지웠다(외부 백업에 있다).

   **같은 설정의 전체 학습을 WSL 로 새로 돌려 끝냈다 (2026-09-12, `runs_wsl/visible`).**
   288 epoch 에서 조기 종료(best 168 + patience 120), 5.0시간. best mAP50-95 0.7428 로
   train-3 과 사실상 같다(위 `models/` 표). 그래서 train-3 을 이어갈 이유는 없어졌다.

   **close_mosaic 구간에 처음으로 닿았는데 이득이 없었다.** 271\~288 epoch(mosaic 끔)
   평균 mAP50-95 0.7360 대 직전 251\~270 평균 0.7363. best(168) 이후로는 0.736 근처에서
   평평했다.

   **데이터를 374장 늘려 한 번 더 돌렸다 (2026-09-14, `runs_wsl/visible-2`).** 설정은
   그대로, train 5,098 / val 1,237. best 가 epoch 202 라 조기 종료 없이 300 까지 갔다
   (202 + 120 > 300), 5.6시간(epoch 중앙값 66초 — 데이터 6% 증가만큼 늘었다). 결과는
   위 `models/` 표. **close_mosaic 은 이번에도 이득이 없었다** — 271\~300 평균 0.7375 대

- 그래서 **평가용 분할과 운영 모델 학습은 따로 생각할 것.** 분할은 모델끼리 비교하는
