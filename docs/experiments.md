2. **용량이 병목이었다. yolo26s 로 갈아탈 것 (2026-09-09).**

   ```
              P        R    mAP50   mAP50-95   train/cls  val/cls
   yolo26n  0.8658   0.7946  0.8575   0.6495      2.000    1.873
   yolo26s  0.9065   0.8473  0.9043   0.7288      1.394    1.384
   ```

   전 지표가 낫고 train/val 손실이 **둘 다** 낮다. s 는 34 epoch 에서 n 이
   184 epoch 걸려 도달한 최고값(0.7053)을 넘었고, 60 에서도 여전히 오르는 중이었다.

   운영 가중치와 비교해도 그렇다. **60 epoch 짜리가 이미 앞선다:**

   | 가중치 | imgsz | mAP50-95 | 추론 |
   |---|---|---|---|
   | n ft960 (현재 `best.pt`) | 960 | 0.7239 | 4.58ms |
   | **s probe 60 epoch** | **640** | **0.7311** | **4.47ms** |

   **추론 비용이 같다.** s@640 이 n@960 과 같은 시간에 돈다.

   클래스별로는 희소 클래스가 오른다 — bus +0.045 / scooter +0.018 / truck +0.011,
   대신 person −0.010 / car −0.011 (원래 강했던 것들).

   **s 에서는 해상도를 올릴 이유가 없다. `predict.imgsz` 를 640 으로 되돌릴 것.**

   | imgsz | mAP50-95 | 640 대비 | (참고) n 은 |
   |---|---|---|---|
   | **640** | **0.7311** | — | 0.7050 |
   | 960 | 0.7294 | −0.0018 | 0.7193 (**+0.0143**) |
   | 1280 | 0.6810 | −0.0501 | 0.6959 (−0.009) |

   n 은 960 이 정점이었지만 s 는 640 이 정점이고, 1280 손실도 5배 크다.
   640 을 두 번 재서 소수 4자리까지 같았으니(val 은 증강이 없어 결정적)
   −0.0018 은 잡음이 아니다. 다만 작아서 "960 이 낫다고 할 수 없다"까지만 말할 수 있다.

   **"용량이 늘어 640 에서도 작은 객체를 잡기 때문"은 틀린 설명이었다.** 클래스를
   크기 순으로 놓고 640→960 변화를 보면 정반대다.

   ```
   motorcycle  317  0.6657 -> 0.6634  -0.0022   <- 가장 작은데 평평
   scooter     176  0.5884 -> 0.6033  +0.0150
   bicycle     281  0.6578 -> 0.6362  -0.0216
   person    4,718  0.7895 -> 0.8034  +0.0139
   car       2,207  0.8733 -> 0.8857  +0.0124
   truck       262  0.7296 -> 0.7467  +0.0171
   bus         219  0.8137 -> 0.7668  -0.0470   <- 가장 큰데 폭락
   ```

   960 은 person·car·truck·scooter 를 올리는데 bus·bicycle 이 그만큼 깎아
   총합이 평평해진 것이다. **왜 bus 가 깎이는지는 아직 설명하지 못했다.**
   그 둘은 박스가 219·281개뿐이라 표본도 얇다. 총합 결론(640 을 쓸 것)만 쓸 것.

   VRAM 실측 (8GB 카드, AMP): s@640 은 **batch 16 이 상한**이다.

   ```
   n 640 b40   6.19 GiB    385 ms/step
   s 640 b40  10.93 GiB   6866 ms/step   <- OOM 없이 페이징. 함정 9 그대로
   s 640 b24   6.61 GiB    650 ms/step
   s 640 b16   4.47 GiB    220 ms/step   <- 실제 학습 259초/epoch
   s 960 b8    5.15 GiB    244 ms/step   <- BN 이 불안정해 권하지 않음
   ```

   **프로브를 이어 가지 않고 본 학습을 새로 돌렸다.** seed2 추가·폴더 이동으로 데이터가
   바뀌어 `labeler.py train` 으로 처음부터 시작했다 — `runs/train-3` (yolo26s / 640 /
   batch 20 / patience 120 / close_mosaic 30). 두 번 이어 붙였고(26·72 epoch 에서)
   **202/300 에서 정지 파일로 멈췄다.** best 는 epoch 158 (mAP50-95 0.7390).
   프로브의 resume.pt 는 2026-09-11 정리 때 지웠다(외부 백업에 있다).

   **같은 설정의 전체 학습을 WSL 로 새로 돌려 끝냈다 (2026-09-12, `runs_wsl/visible`).**
   288 epoch 에서 조기 종료(best 168 + patience 120), 5.0시간. best mAP50-95 0.7428 로
   train-3 과 사실상 같다(위 `models/` 표). 그래서 train-3 을 이어갈 이유는 없어졌다.

   **close_mosaic 구간에 처음으로 닿았는데 이득이 없었다.** 271\~288 epoch(mosaic 끔)
   평균 mAP50-95 0.7360 대 직전 251\~270 평균 0.7363. best(168) 이후로는 0.736 근처에서
   평평했다.

   **데이터를 374장 늘려 한 번 더 돌렸다 (2026-09-14, `runs_wsl/visible-2`).** 설정은
   그대로, train 5,098 / val 1,237. best 가 epoch 202 라 조기 종료 없이 300 까지 갔다
   (202 + 120 > 300), 5.6시간(epoch 중앙값 66초 — 데이터 6% 증가만큼 늘었다). 결과는
   위 `models/` 표. **close_mosaic 은 이번에도 이득이 없었다** — 271\~300 평균 0.7375 대

- 그래서 **평가용 분할과 운영 모델 학습은 따로 생각할 것.** 분할은 모델끼리 비교하는

  person +0.045·car −0.024·scooter +0.015 다.
- **확인하지 않은 것.** 학습은 한 번(seed 0)뿐이라 클래스별 ±0.01 은 잡음일 수 있고, 신뢰구간(이미지 부트스트랩)도 내지 않았다.
  추론 시간은 이 측정에서 재지 못했다 — VRAM 이 거의 찬 채(nvidia-smi 7.9GB) 돌았다. m 은 s 의 약 3.3배 연산이다(fuse 전 22.8
  → 75.0 GFLOPs). 운영으로 올린 뒤 예측 비교(P)와 같은 범위(디코딩 포함, conf 0.25)로 test 10장을 재니 한 장 중앙값이 CPU 는
  s 94ms → m 179ms 였고, GPU 는 50 → 40ms 로 디코딩에 묻혀 차이가 안 보였다(순수 추론 시간은 따로 재지 않았다).
  truck 에서 pickup 이 깎는 몫은 pickup 을 truck 으로 합쳐 다시 재면 가를 수 있다(안 했다).

## 사전학습 가중치의 몫 — 전부·backbone 만·없음을 지금 데이터로 학습해 비교 (2026-11-18, 집 데스크탑)

'새 구조를 짜면 사전학습 가중치를 버리는 것이 아까운가'(사용자 질문 — 비교 학습은 사용자 승인)를 지금 데이터로 쟀다. 같은
yolo26m 구조를 세 갈래로 학습했다: **A** `weights/yolo26m.pt`(COCO)를 전부 얹음 / **B** backbone(0–10층, 10.37M)만 그 값이고
neck·Detect(11.58M)는 새로 초기화 / **C** `yolo26m.yaml` 에서 처음부터(`pretrained=False`).

- **데이터.** 그날 DB 를 읽기 전용으로 복사해 승인 175장 전부를 가릴 영역을 칠한 세트로 만들었다(`tools/build_subset_dataset.py
  --drop-classes --force-split test --paint-masks` — 10클래스, 칠한 136장, 반 넘게 가려진 1,107개를 뺀 박스 867개). 프로젝트의
  `grouping.group_images`(카메라째 + dHash)가 낸 묶음 35개(= 카메라 35대)를 클래스별 박스 수가 비슷하도록 **3묶음**으로 나눠,
  묶음마다 나머지 둘(115–118장)로 학습하고 그 묶음(57·58·60장 — 박스 253·269·345개)으로 평가했다. **진짜 DB 의 분할은 그대로
  미배정이다.** person 은 몇 카메라에 몰려 평가 박스가 22·60·107개로 고르지 않고, scooter 4개는 한 묶음에만 있다.
- **학습.** Windows `.venv`(Ultralytics 8.4.212·torch 2.15.0+cu134·RTX 5060 Ti 16GB). 인자는 config.yaml 의 학습 설정과 같다 — 640·
  batch 10·100 epoch·patience 120·optimizer auto(AdamW lr 0.000714)·cos_lr·box 7.5·cls 1.5·dfl 1.5·close_mosaic 10·증강 값·seed 0.
  다른 것은 `cache=False`·`plots=False` 뿐이다. 실행 둘을 나란히 돌렸다(VRAM 합계 14.2GB, epoch 중앙값 5.7–5.9초로 고르다 — 함정 9 의
  느려짐 없음, 100 epoch 에 약 10분). 11개 실행에 73분.
- **세는 식.** mAP 는 Ultralytics `val` 을 평가 묶음에, 마지막 epoch 가중치(`last.pt`)로 잰 것이다(`best.pt` 는 같은 평가 묶음으로 고른
  것이라 낙관적이어서 따로 적는다). 찾음·클래스까지·헛 박스는 위 '사전학습 가중치에 이미 든 몫' 과 같은 식(`predict`·conf 0.25·
  IoU 0.5 탐욕 짝짓기)으로 센 세 묶음의 합이다(정답 867, 전부 batch 8).

| 갈래 (100 epoch) | mAP50-95 묶음별 (평균) | best.pt 평균 | mAP50 평균 | 찾음 | 클래스까지 | 헛 박스 |
|---|---|---|---|---|---|---|
| A 사전학습 전부 | 0.235·0.333·0.279 (0.282) | 0.319 | 0.381 | 638 (73.6%) | 537 (61.9%) | 195 |

- **전부 버리면(C) 찾는 박스가 A 의 절반이다**(329 대 638), mAP50-95 는 0.080 대 0.282. **더 오래 돌려도 못 따라온다** — 묶음 0 을
  300 epoch 으로: 찾음 80 → 110(A 는 100 epoch 에 194 / 253), mAP50-95 0.068 → 0.082(A 0.235). C 는 300 epoch 을 다 돌았고 best 는 217 이었다.
- **backbone 만 살리면(B) 찾는 수는 A 의 92% 지만 클래스와 박스 정밀도에서 벌어진다** — 클래스까지 452 대 537, mAP50-95 0.173 대
  0.282(39% 낮다). 묶음 0 의 300 epoch 은 patience 로 233 에서 멈췄고(best 113) 0.142 → 0.158, 찾음 181 → 183, 헛 박스 45 → 30 이었다.
- **순서 A > B > C 는 세 묶음 모두에서, mAP 로도 찾음으로도 같다**(mAP50-95 차이가 묶음마다 A − B 0.08 이상, B − C 0.07 이상).
  conf 0.10 에서도 같다 — 찾음 A 684·B 648·C 415, 헛 박스 386·590·768.
- **지금 175장으로 미세조정한 A 는 학습을 안 한 COCO 가중치보다 덜 찾았다** — conf 0.25 에서 638 대 677, conf 0.10 에서 684 대 745 이고
  헛 박스도 더 많다(195 대 96). 벌어지는 곳은 person(80 대 114 / 189)과 responder(16 대 27 / 36 — COCO 가중치는 car·truck 으로 찾는다)이고
  car 는 A 가 낫다(364 대 348 / 406). 운영 m 은 779(person 157)다. 왜 깎이는지는 가르지 않았다(학습 장수, 가릴 영역 밖에 남은 사람 조각이
  배경으로 배워지는지, 640 mosaic 에서 사람이 너무 작아지는지). **운영 m 쪽 수치는 유리하게 나온다** — 이 라벨이 운영 모델의 자동 라벨에서
  출발했다.
- **8.4.212 는 클래스 이름이 같은 분류 출력을 옮긴다.** A 의 로그에 `Remapped 6/10 cls head rows from pretrained weights by class name` 이
  찍힌다 — `BaseModel._remap_cls_by_names` 가 COCO 의 person·bicycle·car·motorcycle·bus·truck 줄을 우리 클래스 자리로 복사한다(B 에서는
  새로 초기화한 값이 옮겨질 뿐이다). 그래서 A 는 2 epoch 만에 묶음 0 에서 196 / 253 을 찾았다. **8.4.142 에 이 동작이 있는지는 확인하지
  않았다** — 버전이 다른 PC 의 학습끼리 견줄 때 볼 것.
- **한계.** seed 하나, 학습 설정 하나(scratch 에 맞춘 lr·일정은 300 epoch 한 번 말고는 안 해 봤다), 640 뿐, 학습 115–118장(전체의 3분의 2).
  `predict` 의 찾음 수는 batch 구성에 따라 1% 쯤 달라진다(COCO 가중치가 batch 4 로 671, batch 8 로 677 — 크기가 다른 이미지가 한 batch 에
  섞이면 레터박스가 달라지는 것으로 보이지만 확인하지 않았다).
- 원자료·스크립트는 `runs/compare_1118_pretrain/` — `results.jsonl`(실행마다 한 줄)·`baseline.jsonl`·`conf_check.jsonl`·실행별
  `*_results.csv`. 다시 돌리려면 그 폴더에 `set/`(위 도구로 만든 세트)과 `work/yolo26n.pt`(AMP 확인이 내려받지 않게)를 두고
  `make_folds.py` → `make_backbone_only.py` → `run_all.sh`. 묶음 목록(카메라 키가 든 파일 이름)과 가중치는 임시 폴더에만 뒀다.

## 출발 가중치와 구조를 바꿔 같은 3묶음으로 — P2 곁가지·Objects365·운영 가중치에서 출발·얼리기 (2026-11-18–19, 집 데스크탑)

위 '사전학습 가중치의 몫' 과 **같은 세트·같은 3묶음·같은 인자·같은 세는 식**으로 갈래를 더했다(사용자 승인 — '② 시험 진행'·
'받아서 시험'·옛 데이터 모델을 파운데이션으로 쓰자는 사용자 제안·'추가'·'25 재보기'). 전부 yolo26m 급·640·batch 10·100 epoch 이고(끝의 25 epoch 일정만 빼고), 따로 적지
않으면 seed 0 이다. 저장소의 코드·설정·DB·`models/` 는 건드리지 않았다(진짜 DB 의 분할은 미배정 그대로).

- **A seed 1** — A(COCO 가중치 전부)를 seed 만 바꿔 다시. 흔들림의 크기를 보려고.
- **P2S (P2 곁가지 — '②')** — yolo26m 의 층 0–22 를 그대로 두고, 층 16(P3 출력)을 2배로 키워 backbone 층 2(P2)와 이어 붙인
  C3k2(256채널) 곁가지(층 23–25)와 4단 Detect `[25, 16, 19, 22]` 를 단 구조(`p2/yolo26-p2side.yaml`). 가중치는 **역할대로** 얹었다
  (`make_p2side_init.py`): 층 0–22 는 이름 그대로, Detect 의 P3·P4·P5 가지는 옛 가지 0·1·2 를 새 가지 1·2·3 으로, P2 가지는 P3 가지의
  복사(분류 마지막 conv 만 새로 — 처음에는 P2 가 조용하다). 새로 초기화한 값은 약 0.20M 개(1% 미만)이고, **학습 전 예측이
  `yolo26m.pt` 와 같다**(16장에서 박스 22 대 22, 좌표·conf 차이 0).
- **P2N (대조)** — Ultralytics 의 `yolo26m-p2.yaml` 에 기본 로더(이름과 모양이 같은 것만)로 COCO 가중치를 얹은 것. 962 텐서 중 420개만
  옮겨진다(backbone 전부와 그 뒤 일부 — 층 번호가 밀려서다).
- **O / OM (Objects365)** — Ultralytics 가 공개한 Objects365 v1 사전학습 가중치 `yolo26m-objv1-150.pt`(GitHub 릴리스 v8.4.0 의 자산,
  45,141,337 바이트, sha256 `e16bb4be917b36071d2b6bccb348887db0f3141fc837a3ee945256100fad9065` — GitHub API 의 digest 와 같다. 체크포인트에
  적힌 학습: 150 epoch·640·batch 128·8.3.222. 사용자 승인으로 이 파일 하나만 받았고 임시 폴더에만 있다 — 저장소·`weights/` 에 넣지
  않았다). **O** 는 그대로(이름이 같은 person·bicycle·car·motorcycle·bus·truck 6줄만 분류 출력이 옮겨진다), **OM** 은 클래스 이름을 우리
  것에 맞춘 사본(`make_o365_mapped.py` — pickup truck → pickup, traffic cone → cone, ambulance → responder(그 줄을 ambulance·fire truck
  두 줄의 평균으로), scooter 를 뺀 9줄이 옮겨진다).
- **F (운영 가중치에서 출발)** — `models/best_y26m_8cls.pt`(COCO → 옛 데이터 학습 3,725장·8클래스)에서 출발. 로그에
  `Remapped 8/10 cls head rows` — responder·cone 두 줄만 새로 초기화된다.
- **FZ11 / FZ23 (얼리기)** — F 와 같은데 `freeze=11`(backbone 층 0–10 — 학습되는 파라미터 11.44M / 21.79M, 52.5%) /
  `freeze=23`(층 0–22 — Detect 만 2.81M, 12.9%). 8.4.212 는 얼린 층의 BatchNorm 통계도 멈춘다(`engine/trainer.py` 의 `_model_train`).
  CPU 로 몇 배치 돌려(`smoke_freeze.py`) 얼린 층의 텐서(FZ23 440개·FZ11 250개, BatchNorm 통계 포함)가 출발 가중치와 전부 같고 안 얼린
  쪽만 바뀐 것을 확인했다.

- **seed 만 바꿔도 묶음 하나의 mAP50-95 가 0.013–0.041 흔들린다**(A: 0.235·0.333·0.279 대 0.260·0.292·0.292 — 평균은 0.282 대 0.281 로

  다시 돌리면 수치가 그대로 나온다(OM 묶음 0 을 두 번 돌려 mAP 0.2606·찾음 193·클래스까지 158·헛 박스 53 이 똑같았다) — 흔들림은
  실행마다의 우연이 아니라 seed 가 정하는 것이다.
- **P2 곁가지(②)는 지금 데이터·640 에서 채택할 근거가 없다.** 두 seed 평균으로 mAP50-95 0.296 대 0.282(+0.014 — 묶음·seed 여섯 짝의
  차이는 −0.001 부터 +0.039), 찾음 650 대 641, 헛 박스 277 대 232. conf 0.5 로 헛 박스를 비슷하게 맞추면 찾음 582·581 대 575·576 이다.
  이득이 두 seed 모두에서 보이는 곳은 짧은 변 8–16px 뿐이고(154·156 대 145·147 / 228 — 다만 구조를 안 바꾼 O·OM 도 155·156 이다),
  **8px 미만은 오히려 적다**(42·37 대 46·45 / 87). 값은 학습 VRAM 11.7GB(A 6.2GB)와 연산량 1.6배다. 작은 물체에는 입력 크기가 훨씬
  컸다(위 절 — 학습 없이 1280 으로: 운영 m 779 → 810, COCO 677 → 767).
- **구조를 바꿀 때 가중치를 역할대로 옮기는 값은 크다** — 같은 P2 계열인데 기본 로더(P2N)는 0.193 으로 A 보다 0.089 낮고(B 의
  0.173 근처 — backbone 만 옮겨진 셈이다) 역할대로 얹은 P2S 는 A 이상이다. P2N 은 1 epoch 뒤 0.000 에서 시작한다(P2S 0.279·0.207).

## SAM 클릭 모델 비교 — sam2.1_t·sam2.1_s·SAM 3.1·작은 것만 잘라 다시 (2026-11-25, 집 데스크탑)

사용자 질문 '더 큰 sam2.1_s 로 바꾸면 얼마나 나아지나, SAM 3.1 을 쓰면 어떻게 되나' → '받아서 재기'. 검수 화면의 SAM 클릭(`C`·`R`)은
