## 출처 단위('카메라')

분할과 평가의 단위다. 형태마다 무엇을 한 단위로 볼지가 다르다.

| kind | 한 단위 | 예 |
|---|---|---|
| `cctv` | 고정 카메라 한 대 | 교차로 기둥 카메라 |
| `phone` | 한 장소에서 한 번 나가 찍은 묶음 | 어느 날 한 주차장에서 찍은 사진들 |
| `screen` | 캡처한 화면의 원 카메라(모르면 캡처 원천 하나) | 공개 CCTV 웹 뷰어의 한 채널 |
| `dataset` | 공개 데이터셋의 장면 | VIRAT 장면 `0002` |

같은 장소라도 카메라가 다르면 다른 단위다. 폰으로 같은 장소를 다른 날 다시 찍으면 **같은 단위로 등록할 것** —
다른 단위로 두면 같은 배경이 train 과 test 로 갈린다.

## 폴더 규칙

```text
data/visible/unlabeled/<카메라키>/[<YYYYMMDD>/]<파일>
```

- 카메라키는 `cameras.yaml` 의 키 그대로, 영문 소문자·숫자·`-` 만(`^[a-z0-9][a-z0-9-]*$`) — 폴더 이름이 되므로
  한글·공백을 피한다.
- 날짜 폴더는 정리용이고 없어도 된다(시각은 아래 순서로 따로 읽는다).
- `unlabeled/` 바로 아래 둔 파일은 지금처럼 출처 없이(`source='unlabeled'`) 들어가고 scan 이 경고한다.
- 11-03 전 tidy 는 승인분을 `labeled/images/` **한 폴더에 평평하게** 옮겼다(`tidy.tidy_approved` → `_free_name`). DB 의
  `camera` 열은 남지만, DB 를 잃으면 `labeled/` 만으로는 카메라를 되찾을 수 없다 — 그래서 tidy 가 카메라 폴더를
  유지하게 바꿨다(`labeled/images/<카메라>/…` ↔ `labels/<카메라>/…`, 구현 순서 1).

## 등록 파일 `data/visible/cameras.yaml`

**저장소(public)에 담지 않는다** — `data/` 아래라 이미 `.gitignore` 대상이고, 다른 디스크 백업(robocopy)에는 들어간다.
설치 장소를 적으므로 이 파일과 그 내용을 커밋·업로드하지 말 것.

```yaml
cameras:
  pg-cross-01:            # 키 = 폴더 이름
    kind: cctv            # cctv | phone | screen | dataset
    place: 판교 ○○ 사거리   # 장소 이름만. 좌표 금지
    mount: pole           # pole | rooftop | wall | indoor | drone | handheld | unknown
    view: 교차로 북쪽, 부감 약 30도   # 자유 서술
    resolution: 1920x1080
    tz: '+09:00'          # 시각 해석 기준(UTC 와의 차이). 기본 +09:00. KST·JST·UTC·GMT·Z·'UTC+9'·'+9'·Asia/Seoul 도 받는다(11-10, normalize_tz) — CST·IST 처럼 뜻이 여럿이거나 EST·PST 처럼 여름에 바뀌는 약어는 오프셋으로. 그 밖의 이름(America/New_York)은 이 PC 에 tzdata 가 없어 안 풀린다
    rights: 직접 촬영      # 권리자·라이선스·사용 조건
    split:                # 비우면 자동(카메라째 한 분할). train|val|test 로 고정할 수 있다
    note:
  virat-0002:
    kind: dataset
    place: VIRAT scene 0002
    mount: rooftop
    rights: VIRAT Release 2.0 — 개인별 동의 약관, 재배포 금지로 볼 것
```

- 속성은 이 파일 하나에만 둔다. DB 에는 키만 남긴다(두 곳에 두면 어긋난다).
- 키를 바꾸려면 폴더 이름과 DB `images.camera` 를 같이 바꿔야 한다 — 되도록 바꾸지 말 것.

## DB 변경

`images` 에 열 둘을 더한다(`ALTER TABLE ADD COLUMN` — `split`·`grp`·`dhash` 때와 같은 방식, 기존 행은 그대로).

| 열 | 값 | legacy |
|---|---|---|
| `camera` | 카메라키 | NULL |
| `captured_at` | 촬영 시각 ISO 8601, 시간대 포함(`2026-11-03T14:05:12+09:00`) | NULL |

- 카메라 폴더로 들어온 이미지의 `source` 는 **`collected`** — 정할 때(11-03)는 `source='unlabeled'` 가 `tools/test_baseline.py`
  에서 '비CCTV' 를 뜻해서 새 CCTV 를 거기 섞지 않으려 했다. 11-04 부터 test_baseline 의 CCTV·드론·비CCTV 는 사람이 정한
  `images.domain`(비어 있으면 카메라 등록으로 짐작)이고, `source` 는 `legacy`(seed·unlabeled)와 `collected` 를 가르는 데
  쓴다. 공개 데이터셋은 지금처럼 데이터셋 이름(`o365`, `virat`)을 쓴다.
- `ingest_batch` 는 경로가 이미 있으면 `source` 를 다시 쓴다(`store.py`) — `camera`·`captured_at` 은 **처음 넣을 때만**
  쓰고 덮지 않는다.

## 촬영 시각 읽는 순서

처음 걸리는 것을 쓴다. 못 찾으면 NULL(모름) — **파일 수정 시각은 쓰지 않는다**(복사·다운로드 때 바뀐다).

1. 파일 이름의 시각 — `..._YYYYMMDD_HHMMSS[_mmm]`(아래 프레임 추출 도구가 쓰는 형식), 폰 `YYYYMMDD_HHMMSS`,
   Windows 캡처 `스크린샷 YYYY-MM-DD HHMMSS`(`grouping.py` 가 이미 읽는 꼴).
2. EXIF `DateTimeOriginal`(+ 있으면 `OffsetTimeOriginal`) — 폰·카메라 사진.
3. 없음.

시간대가 없는 값은 카메라의 `tz` 로 해석한다.

## 영상 → 프레임: `tools/extract_frames.py`

```bash
.venv/Scripts/python.exe tools/extract_frames.py <영상> --camera pg-cross-01 --start "2026-11-03 14:00:00" --every 5
```

- `unlabeled/<카메라>/<YYYYMMDD>/<카메라>_<YYYYMMDD_HHMMSS>_<mmm>.jpg` 로 쓴다(시각 = 시작 + 프레임 시각).
- `--start` 를 빼면 영상 이름에서 시각을 찾고, 없으면 멈춘다(시각 없는 프레임을 만들지 않는다).
- 간격은 기본 5초(`--every`, 0·5·10초… 격자). 같은 이름이 있으면 건너뛰어 다시 돌려도 결과가 같다. `--dry-run` 은 셈만 한다.
- **거의 같은 프레임 건너뛰기는 기본으로 끈다.** dHash 거리 2 이하로 건너뛰게 짰다가, VIRAT 옥상 영상에서 5초 간격
  138장 중 125장이 걸렸다 — 8x8 dHash 는 화면 속 작은 사람·차를 못 본다. 대신 `--min-change <퍼센트>` 를 주면 직전
  저장 프레임과 비교해 밝기가 20 넘게 바뀐 픽셀 비율(가로 320px)이 그보다 작을 때 건너뛴다. 같은 영상 137쌍의 비율은
  중앙값 0.77%, 0.05% 미만(사실상 같은 화면) 22쌍 — 똑같은 화면만 빼려면 0.05 정도다. 바이트까지 같은 프레임은
  scan 의 중복 검사(dupcheck)가 어차피 막는다.
- 실측(11-03): VIRAT `VIRAT_S_000001.mp4`(1080p, 29.97fps, 11.5분)를 끝까지 훑는 데 32초.
- **검수 UI 의 '영상 캡처' 탭(11-10, 사용자 요청 — README '영상 캡처')** 이 같은 방식으로 뽑아 눈으로 고른 것만 넣는다 — 같은
  영상을 2초마다 뽑은 10장이 이 도구의 결과와 이름·바이트까지 같았다(hw-02 구간 영상). 다른 점: 영상을 서버에 사본으로 올려
  뽑는다(넣거나 닫으면 지운다), `--min-change` 대신 칸마다 바뀐 픽셀 비율을 보여 주고 '…% 미만 빼기' 로 한꺼번에 뺀다, 픽셀까지
  같은 프레임은 처음부터 뺀다, 넣은 뒤 곧바로 스캔한다. 시작 시각은 영상 이름 → 사람이 적은 값(파일 수정 시각 − 길이는 버튼으로
  제안만)이고, **모르면 비워 둘 수 있다**(11-10 사용자 요청 — 시각 정보가 없는 영상): 이름이 `<카메라>_v<영상 지문 8자>_t00h01m05s500.jpg`
  (폴더 `v<지문>/`, `capture.notime_name`)가 되어 `captured_at` 은 NULL 이다 — 이 도구의 '시각 없는 프레임을 만들지 않는다' 와 달리
  사람이 고른 것이고, 나중에 이름으로 채울 수 없다. 같은 VIRAT 영상을 10초마다 뽑아 화면에 띄우기까지 44초였다(JPEG 쓰기·썸네일 포함).

## 분할

- `grouping.group_images` 에서 **같은 카메라는 하나로 합친다**(지금의 연번·연사·dHash 합집합에 하나를 더한다).
  그래서 카메라 하나 = 묶음 하나(dHash 로 다른 이미지와 이어지면 더 커진다).
- **이름 계열(연번·30초 연사)은 카메라 안에서만 잇는다**(11-05) — 다른 카메라 폴더의 `IMG_####`·스크린샷·`frame_####`
  같은 이름은 번호나 시각이 이어져도 한 묶음이 되지 않는다. 서로 다른 카메라는 dHash 로만 이어질 수 있다(고정 분할이
  다른 카메라가 그렇게 이어지면 아래처럼 분할이 멈춘다).
- 이름을 견줄 때 로보플로 꼬리표는 이중(`_png_png.rf.<해시>`)까지 다 떼고, 영문 `Screenshot …` 이름도 30초 스크린샷
  규칙에 든다(11-05).
- `cameras.yaml` 의 `split` 이 있으면 그 묶음은 그 분할로 고정한다. 없으면 지금의 계층화가 묶음째 배정한다.
- **기존 이미지는 움직이지 않는다**는 규칙은 그대로다. 새 카메라 묶음이 dHash 로 legacy 묶음과 이어지면 옮기지 않고
  `[알림] … 두 분할에 걸칩니다` 로 알린다.
- 카메라가 적은 동안은 15% test 가 카메라 한두 대로 정해져 비율이 크게 틀어질 수 있다 — split 보고에 카메라별
  배정을 찍어 보이고(`카메라별: …`, 두 분할에 걸친 카메라는 `[경고]`), 필요하면 `split:` 으로 직접 고정한다.
- 고정은 다수결보다 앞선다. 다만 **이미 다른 분할에 있던 이미지는 옮기지 않고** `[알림] … 옮기지 않았습니다` 로
  알린다(기존 배정 고정 규칙). 고정이 서로 다른 카메라가 dHash 로 한 묶음이 되면 어느 쪽도 지킬 수 없어
  **분할을 멈춘다** — `split` 도 `grp` 도 쓰기 전에 멈춘다. 등록 파일이 깨졌을 때도 같다.
- 확인(11-03): 실제 DB 사본 두 개에 옛 코드(`b149bcb`)와 새 코드로 `ensure_splits` 를 돌려 승인 6,567장의 `grp`·`split`
  이 한 행도 다르지 않았다(legacy 는 카메라가 없어 결과가 같아야 한다).

    (`ah-` 로 시작하는데 그 꼴이 아닌 키 — `ah-101` — 는 둘 다에서 빠져, 같은 날 Gemini 리뷰 뒤로 `--pin-train`·`--check`·넣는
    실행이 그런 키를 알린다. '밖으로 보내지 않는다'(`label_qa_claude` 의 `local_only`)만은 그날부터 `ah-` 로 시작하는 키를
    전부 막는다 — 전에는 `ah-NNNN` 만 막아, 키를 틀리게 등록한 그림이 나갈 수 있었다). 중복은 그날 진짜 DB 로 쟀다: **바이트가 같은 그림은 scan 이 등록하지 않는다**(넣기 전에는
    `labeler.py dupcheck --folder <폴더>` — 넣은 100장의 원본 100장을 전부 '이미 있음' 으로 잡았다. DB 안의 같은 그림은 0묶음).
    **같은 영상의 다른 프레임은 못 잡는다**(그 영상들의 옆 프레임 80장 중 0장 — 바이트가 다르다). 이름 앞머리(`<영상 id>_<클립>_`)가
    같은지로 봐야 한다.
    - **넣기 전 점검 `tools/import_aihub_pm.py --check <폴더·파일…>` (같은 날 사용자 요청으로 만들었다 — 아무것도 쓰지 않는다).**
      고른 그림마다 DB 와 견줘 **같은 그림**(바이트)·**같은 영상**(이름의 영상 id)·**같은 자리**(`same_camera`)를, 함께 준
      파일끼리도 같은 셋을 이름·카메라 키·이미지 번호로 알린다(목록 `<DB 폴더>/aihub_pm/check_<시각>.tsv`). 그날 진짜 DB 와
      AI Hub 원본으로 돌려 봤다: 넣은 프레임의 원본 3장 → 같은 그림 3, 넣은 영상의 다른 프레임 2장 → 같은 영상 2, **넣은 적 없는
      영상 12개의 프레임 → 새 것 6 · 같은 자리 5 · 준 것끼리 같은 자리 1**(17장에 18초 — DB 의 AI Hub 100장 지문 읽기 포함).
      영상이 처음이어도 절반은 이미 있는 카메라 자리였다. **'같은 자리' 는 넉넉하게 잡는 어림이다** — 다른 장소를 같다고 할 수
      있고(그래서 알려 준 번호의 그림을 검수 화면에서 사람이 견줘 본다), 판정이 이어지지도 않는다(가 ~ 나, 나 ~ 다 인데 가 ≁ 다).
      **같은 날 Gemini 리뷰로 고친 것:** 함께 준 앞의 파일과 바이트가 같은 파일(이름만 바꾼 사본)이 '준 것끼리 겹침' 으로만
      나와, 앞의 파일이 '같은 자리'·'같은 영상' 이어도 사본은 가볍게 보였다 — 이제 앞의 파일의 판정을 그대로 받는다. 못 읽는
      파일은 '준 것' 으로 세지 않는다(같은 영상의 읽히는 파일·같은 바이트의 다른 깨진 파일을 겹침으로 만들었다). **DB 가
      없으면 멈춘다** — 전에는 `--config` 를 잘못 주면 빈 DB 를 새로 만들어 '전부 새 것' 이라고 했다(점검의 답이 거꾸로
      '안전' 이 된다). 보기만 하는 실행은 DB 를 읽기 전용으로 연다.
    - **DB 의 AI Hub 그림은 출처가 `aihub_pm` 이거나 카메라 키가 `ah-NNNN` 인 것이다**(`import_aihub_pm.known`, 그날부터) —
      점검도, 넣는 실행의 '이미 넣은 영상·같은 자리 건너뛰기'(`existing`)도 이 목록을 쓴다. 그 전에는 출처만 봐서, 손으로 넣은
      그림과 같은 영상·자리를 도구가 다시 고를 수 있었다.
  - 더 넣으려면 같은 명령을 다시(이미 넣은 영상·같은 자리는 건너뛰고 번호가 이어진다, `--scale` 로 몫). 검수 대기를 지금 모델로
    다시 라벨링하는 길(`--relabel`)은 만들지 않았다 — `labeler.py label --all` 은 후보를 지우니 쓰지 말 것.

## 국가교통정보센터(ITS) CCTV Open API (2026-11-24 조사 — 가져온 그림은 없다)

사용자가 its.go.kr 오픈데이터의 인증키를 받았다(계정당 1개, 'CCTV 화상자료'·'돌발상황정보' 를 골랐다). **키는 집 데스크탑의
사용자 환경 변수 `ITS_API_KEY` 에 있다** — 값을 읽거나 찍지 말 것. 키가 요청 주소의 `apiKey=` 에 들어가니 그 주소를 로그·파일·git 에
남기지 않는다. 아래 수치는 11-24 14시 반쯤 API 를 6번 불러 잰 것이고(스크립트·인자는 `runs/its_probe/`), 근거 문서는 그 사이트의
'CCTV API 제공 기술기준' v1.0(2026-08-07)이다. 그림은 한 장도 저장하지 않았다 — 수집 도구는 아직 없다(docs/next.md 7번).
그날 받은 목록 5개·돌발 목록·카메라별 크기(`census_ex.json`·`census_its.json` — 번호·이름·좌표·크기)는 git 밖
`data/visible/its/20261124/` 에 뒀다(12 MB. 목록 속 영상 주소는 하루 뒤 죽지만 번호·이름·좌표는 남는다 — HD 카메라를 고를 때,
번호가 날마다 같은지 볼 때 쓴다).

- **부르는 법:** `https://openapi.its.go.kr:9443/cctvInfo?type=ex|its&cctvType=1..5&minX…maxY&getType=json`. 전국 상자
  (124–132°E · 33–39°N)를 주면 **한 번에 전부 온다**(2–3초, 2–3 MB) — 고속도로(ex) 4,699\~4,700대, 국도(its) 6,500대. 지방도·
  시군도는 제공 대상이 아니다. 로컬 스크립트에서 그대로 됐다(신청 화면의 '사용처' 는 센터 Q&A 가 따로 없으면
  `http://localhost` 로 적으라고 답했다 — Origin·Referer 머리 없이 부른 호출이 됐다).
- **칸:** `cctvname`(실제 지명 — **git 에 넣지 말 것**, `cameras.yaml` 의 `place` 로만)·`coordx`·`coordy`·`cctvurl`·`cctvformat`.
  **`cctvresolution`·`filecreatetime`·`roadsectionid` 는 전부 빈칸이다** — 해상도는 받아 봐야 안다.
- **주소 첫 칸의 번호가 카메라다.** 정지·실시간·동영상 목록에서 같은 번호는 이름·좌표가 전부 같았다(고속도로 4,698 / 4,698,
  국도 6,499 / 6,499 — 목록끼리 한두 대는 들고 난다). 뒤의 토큰은 목록마다 다르고 24시간만 유효하다(기술기준). **날이 바뀌어도
  번호가 같은지는 아직 안 봤다.** 이름은 고속도로 16개·국도 10개가 여러 번호에 겹치고 좌표는 한 점에 11대까지 겹친다 — 카메라
  키는 이름·좌표가 아니라 번호로 잡을 것.
- **cctvType 마다 오는 것** (1·2 는 4·5 의 http 판이라 부르지 않았다):
  - **3 정지 영상(JPEG)** — `http://…:8090/<번호>/<토큰>` 과, 문서에 없는 `cctvurl2`(같은 경로의 https `:8091`). Range 요청이 된다.
    그림은 그 카메라 영상과 같은 크기다(아래). **몇 초마다 새로 찍히지는 않는다** — 고속도로 3대를 12초 간격으로 4번 받으니
    한 대만 그림이 바뀌었고 두 대는 36초 내내 같았다(바뀌는 주기는 못 쟀다. `Last-Modified`·`ETag` 도 없다).
  - **4 실시간(HLS, https)** — 화질 단계는 하나뿐이고 H.264 다. OpenCV(FFmpeg)가 주소를 그대로 연다(여는 데 1초 안팎).
    고속도로(3대): 2–3.5초 조각 7개(약 20초 분량), 조각마다 `EXT-X-PROGRAM-DATE-TIME`(KST 시각)이 있다, 0.8–1.1 Mbps,
    30fps(한 대는 17fps). 국도(6대): 14–16초 조각 60개 — **지난 15분이 재생 목록에 남아 있다**, 시각 표시는 없다,
    720×480 은 0.26–2.1 Mbps · 1920×1080 은 4.1–4.2 Mbps.
  - **5 동영상(mp4, https)** — **가장 최근 약 30초짜리 파일**이다(고속도로 3대: 29.6–29.9초, 2.9–3.8 MB, 720×480, Range 됨).
    영상 파일을 받는 `tools/extract_frames.py`·`tools/auto_capture.py` 에 그대로 넣을 수 있는 꼴이다. 국도는 안 봤다.
- **해상도 — 정지 영상의 머리 4KB 만 받아 전부 쟀다** (11,199대 중 11,196대, 국도 3대는 404. 받은 양은 46 MB):

  | 크기 | 고속도로 4,699대 | 국도 6,497대 |

  | 720×480 | 4,356 (92.7%) | 6,002 (92.4%) |
  | 1280×720 | 124 | 245 |
  | 1920×1080 | 7 | 39 |

  **높이 720 이상은 423대(3.8%)이고 그중 1080p 가 46대다.** 실시간 영상도 같은 크기였다 — 1080p 3대(국도)·720p 2대(고속도로)·
  720×480 급 6대를 OpenCV 로 열어 확인했다. 키를 받기 전에 공개 지도(`its.go.kr/map/cctv`, 같은 CDN)에서 잰 것과도 같다
  (고속도로 한 노선 30대 전부 720×480, 국도 한 노선 14대 중 3대가 1280×720). 그 지도의 재생기는 고속도로 한 대를 853×480
  으로 알렸다(720×480 을 16:9 로 늘려 보이는 것으로 보인다 — 옛 ROAD PLUS 녹화가 SD 였던 것과 같은 급이다).
- **돌발상황정보 `…:9443/eventInfo?type=all&eventType=all`** (같은 키, 15초 걸렸다) — 그 시각 전국 470건, 전부 좌표가 있다.
  고속도로 357(공사 278 · 재난 38 · 기타돌발 22 · 기타 11 · 기상 6 · 교통사고 2) · 국도 72(공사 71 · 교통사고 1) · 시군도 24 ·
  기타 12 · 지방도 5. `message` 는 '(갓길)고장차 처리중'·'(5차로) 승용차 사고 처리중'·'(갓길)이동 차선도색 작업중' 같은 글이다
  (재난·기상은 강풍·적설 알림). **가장 가까운 CCTV 까지** (좌표끼리 잰 거리 — 그 카메라에 현장이 보이는지는 안 봤다):

  | 고속도로 기타돌발 (고장차 등) | 22 | 15 | 19 | 21 |

  시군도·지방도의 돌발(29건) 근처에는 카메라가 없다(제공 대상이 아니다). responder·cone 이 모자란 것을 채울 때 — 돌발 지점
  근처 카메라만 골라 받는 길이 된다(해 보지는 않았다).
- **이용 조건 (11-24 에 읽은 것 — API 로 받은 그림을 저장·학습에 쓰는 것, 밖으로 올리는 것을 직접 다룬 글은 못 찾았다):**
  - 기술기준: 실시간만 준다(과거 영상은 도로 관리기관 소관), 주소는 24시간, **연속 재생 시간과 동시 스트리밍 수가 제한될 수
    있다**고만 적혀 있다(수치 없음).
  - 사이트 '저작권보호': 무단 복제·배포 금지, 영리 아닌 개인 이용의 복제는 가능, 단체가 내부에서 쓰려는 복제는 불허.
    회원 약관 14조: 센터 동의 없이 영리 목적으로 쓰면 이용을 제한할 수 있다.
  - 공공데이터포털의 행안부 연계 항목(`data.go.kr/data/15150341` — 국가교통정보센터가 제공하는 정보라고 적혀 있다)은
    '이용허락범위 제한 없음'.
  - **그래서 받은 그림은 git 밖에만 두고, 밖(Runpod·Roboflow 등)으로 올리기 전에는 사용자에게 물을 것.**
- **한도:** 월 호출 한도는 신청 때 고른다(개발용 100건 · 운영용 1,000건 — 사용자가 어느 쪽으로 받았는지는 듣지 못했다),
  늘리려면 인증키 상세정보에서 사유를 적어 요청한다(센터 Q&A 답변). 호출 한 번이 전국 목록이라 주소 갱신은 하루 2번(ex·its)이면 된다. 응답에 남은 횟수를 알려 주는 머리는 없다 —
  한도가 서비스별인지 키 전체인지는 모른다(FAQ 의 '서비스별 월 1,000건, 보통 30,000건으로 승인' 은 지금 신청 화면과 달라 옛 글로
  보인다).
- **재생 제한을 건드려 본 것 (작게만):** 고속도로 실시간 한 대를 5분 이어 읽어 끊기지 않았고(9,104프레임 — 30fps), 4대를
  한꺼번에 30초 읽어 넷 다 끊기지 않았다. 그보다 길게·많이는 해 보지 않았다 — 기술기준이 제한할 수 있다고 적어 둔 곳이니
  수집 도구는 짧게 받고 끊는 쪽으로 짤 것(최근 30초 mp4, 국도의 15분 재생 목록).
- **안 본 것:** 밤·비 화면, 화면에 박힌 글자(지명·시각)의 자리, 번호가 날마다 같은지, 국도의 mp4, 돌발 지점이 그 카메라에
  실제로 보이는지, 긴 시간·여러 대 녹화의 실제 한도.
